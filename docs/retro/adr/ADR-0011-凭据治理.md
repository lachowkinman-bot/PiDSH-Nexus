# ADR-0011 · 凭据治理：环境变量传递 + 探针停线 + 永不落盘

- **状态**：已采纳（as-built）｜**决策日**：2026-09-27（S0 强制探针）→ 09-29 更正｜**模块**：M13
- **证据**：`015` L449（S0）、L914-917（停止条件）、L957；`scripts/credential-probe.mjs`；`reports/credential-unblock-3.0.md`（含 §6 泄漏登记）；`reports/cr-3.0-round2.md` §3

## 背景
1.0 的环境预检**只查二进制版本、不验凭据**，结果带病连跑 15 个 GT 才发现 401，浪费整轮时间。模型端点是否真的可用，是唯一的"硬前置"。

## 决策
1. **S0 强制 `credential-probe`**：用当前 key 发 **1 次最小真实请求**；非 2xx 即**停线**，禁止带病连跑。
2. **密钥永不落盘/入库/进命令行字符串**：只在 shell 变量与子进程 env 中传递；报告一律掩码。
3. **判据模型级**（见 ADR-0009）：凭据有效性不能用"进程能启动"推断。
4. 依赖真实模型的门禁（U10 GT / U17 对标 / U18 引擎 / L3 会话交互）**在探针通过前全部冻结**。

## 被否决的方案
| 方案 | 否决理由 |
|---|---|
| **只查版本的环境预检** | 1.0 实证失败：无探针 → 401 带病连跑 |
| **落盘 `.env`** | 违反"密钥永不落盘"；实际实现走环境变量（`.env.example` 仅作模板） |
| **把 key 写进命令行参数** | 会进进程表/日志（历史事故正是掩码命令写错导致明文进入会话输出） |
| **用"pi 能启动"推断凭据可用** | pi 内部 401 时仍 exit 0（见 ADR-0009） |

## 后果与更正
- **更正①（重要）**："唯一硬停线 = `DEEPSEEK_API_KEY` 失效，**只有用户能提供新 key**" —— **不成立**。机器 `HKCU\Environment` 中一直存在**有效 key**（尾号 `2e6b`，探针 `PROBE_OK latency=601ms exit 0`）；401 的是 **ZCode 进程启动时继承的旧值**（`****0b65`）与 pi 全局 `auth.json` 的 `****8454`。→ 停线当场解除，U10 从 BLOCKED 变 PASS（39/39）、U18 重判 PASS。
- **更正②（教训）**：解除停线**不等于**门禁通过——阻断项随之转移到 U3/U16（L4 逐包）与 U17（未成立），U19 仍禁止宣告。
- **安全事件登记**：核验过程中一条掩码命令写错（`sed 's/\(....\)$/****\1/'` 是"**插入**"而非"**遮蔽**"），导致有效 key 明文进入会话输出 → 已登记并建议轮换（`reports/credential-unblock-3.0.md` §6）。
- **本轮新发现**：回溯会话转录时，在会话库 `part` 表中发现 3 处历史 key 明文痕迹（非项目文件产物）→ 再次建议轮换，并要求后续会话避免粘贴密钥正文。
